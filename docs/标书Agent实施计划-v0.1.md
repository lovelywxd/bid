## 1. 实施目标与顺序

交付一个本机使用的独立标书应用：从真实资料导入到可审核、可恢复、可追溯的技术标 Word 交付。

原技术基线为 Python 后端、React 前端、PostgreSQL 业务存储、LangGraph 工作流、直接模型接口。本轮新增 Harness 优先验证顺序，采用条件和替换边界见第 12 节；条件满足前不宣布基线切换，也不并行建设两套完整执行栈。先串行完成解析、规划、写作、审核，不启动多个自治 Agent。

长任务方案确定为：持久化父任务统筹进度，按节/条款组建立独立子任务；每个子任务重建上下文，跨任务使用结构化记忆和来源引用，必要时对执行历史做受控摘要。所有步骤均有产出校验，具体契约见第 4.6—4.9 节。

按四个里程碑推进：

| 里程碑 | 完成内容 | 通过条件 |
|---|---|---|
| M1：业务与执行基础 | 样本协议、项目、版本、任务持久化、模型网关、最小界面 | 重启后能恢复已提交状态；重复任务不重复提交 |
| M2：少量章节完整闭环 | 结构解析、要求、证据、写前设计、细目录、上下文、写作、补资料、审核、Word 与人工放行 | 先验代表章节的方案成立、细目录合理、内容讲清楚及客户口径，再完成约三节真实闭环，含一次补资料恢复；未通过不扩大整本写作 |
| M3：整本与变更可靠性 | 补遗传播、编辑冲突、故障预算、完整界面、全链路回归 | T01—T30 执行完成，整本交付通过人工验收 |
| M4：收益验证 | 留出项目、三组对照、人工工时和成本报告 | 给出继续投入、缩减范围或停止扩展的证据与结论 |

M1 就实现状态与恢复，M2 就实现证据、人工介入和审核。M3 完善精确变更传播和故障覆盖，不把这些能力推迟到产品完成后才补。

## 2. 技术与模块边界

### 2.1 固定的工作方案

| 部分 | 实施选择 | 边界 |
|---|---|---|
| 后端 | Python、FastAPI、Pydantic、SQLAlchemy、Alembic；uv 管理依赖 | 业务服务拥有事实、版本、状态和放行规则 |
| 前端 | React、TypeScript、Vite；pnpm 管理依赖 | 项目工作台＋常驻对话；对话绑定正文/要求/问题对象，复用同一业务操作及验收服务 |
| 数据库 | PostgreSQL＋pgvector | 关系数据为主存；首版向量精确检索，暂不建设近似索引 |
| 词法检索 | jieba 中文分词后写入 PostgreSQL simple 配置的词项索引；标识字段精确查询 | 与向量结果融合；证书号、型号、项目名不只依赖相似度 |
| 文件存储 | 本机持久目录，按内容哈希寻址 | 原件、解析产物、图片、模型响应和交付分开保存 |
| 工作流 | LangGraph＋PostgreSQL checkpointer | checkpoint 保存执行引用；业务正文、事实和审核保存在业务表 |
| 调度 | 单个 worker＋数据库任务租约 | API 只提交任务；不依赖 HTTP 请求存活，不先引入 Redis/Celery |
| 模型调用 | ModelGateway，接入试点配置指定的一家提供商原生接口 | 用结构化契约隔离提供商；不自研通用 Agent SDK |
| 文档解析 | Docling 结构转换；DOCX 补充 OOXML 对象定位；本地 RapidOCR 处理扫描内容 | 输出统一 SourceBlock；准确性以样本核对为准 |
| 正文格式 | 有稳定 block_id 的 JSON 内容块：段落、列表、表格、图片 | 应用编辑、锁定和 Word 导出使用同一份结构 |
| Word | python-docx 根据内容块和模板生成整本 | 不使用逐章 Word 的裸 XML 拼接 |
| 渲染 | 固定字体环境的 LibreOffice＋Poppler；UNO 更新目录/字段并另存后转 PDF | PDF 预览必须来自最终待交付 DOCX |
| 测试 | pytest、真实 PostgreSQL 集成测试、Playwright、固定材料评估 | 替身测试与真实模型/真实文档结果分别标记 |

LangGraph 的 checkpoint 用于恢复执行，不替代应用业务数据。[S1] 中断节点恢复时可能重跑节点，写入必须幂等。[S2] Docling 可表达表格、图片、层次与来源信息，并可配置本地 RapidOCR 模型，仍需业务样本验证。[S3][S7] pgvector 支持精确检索，先以此建立检索基准。[S4] python-docx 负责内容装配；LibreOffice 负责更新目录/字段与转换，转换成功仍须检查成品。[S5][S6][S8]

M1 锁定实际可运行的 Python、Node、数据库、依赖、OCR 模型、字体和容器版本，提交锁文件及模型资产校验值；不依赖浮动 latest 标签。模型名称、API 地址、向量维度和预算是试点配置，不在计划中假定用户已选定。

## 3. 业务对象与一致性规则

### 3.1 核心对象

所有可修订对象使用稳定逻辑 ID＋不可变 revision_id；关系引用具体版本。人工确认记录 actor、时间和依据。企业、项目、产品和可用状态是服务端查询条件，不能只靠提示词隔离。

| 对象 | 核心字段/关系 |
|---|---|
| Project / Baseline | 企业、客户、卷册、产品范围、提交时点、当前基线；基线固定要求、资料与决定版本 |
| KnowledgeBaseRevision | 企业/产品/版本、已发布材料及事实版本集合、确认记录、取代关系；被项目基线显式引用 |
| DocumentRevision | logical_id、sha256、角色、来源、企业/项目范围、有效期、supersedes、解析版本 |
| SourceBlock / ParseUnit | 文档版本、稳定块路径、类型、顺序、标题、原文、表格行列跨度、页码/区域、处理状态 |
| RequirementRevision / ScoringItem | 原文引用、条件、类别、是否实质性、卷册、分值/规则、补遗关系、生效状态 |
| FactRevision / EvidenceLink | 结构化事实、产品版本/有效期、所支持的原文、确认状态、引用是否真正支持事实 |
| DecisionRevision | 项目约定、适用范围、确认人、依据、取代关系；与企业能力事实分开 |
| Section / SectionTask | 大纲与顺序、对应要求、前置依赖、写作目标、证据、缺口、当前正文版本 |
| SectionDesignRevision / ResponseAssessment | 章节类型、客户问题、方案机制、能力/项目设计区分、细目录、展开问题及依据；逐要求覆盖/解释/证据三轴状态、缺失问题及正文位置 |
| DraftRevision / ContentBlock | 父版本、正文 JSON、稳定 block_id、锁定块、作者、输入指纹、发布状态 |
| Claim | 正文版本/块位置、类型、主体、数值/单位/条件、证据或决定引用、核验状态；正向保证/负向限制、必要性、责任及范围 |
| ReviewIssue / ReviewRun | 问题编号、严重度、位置、依据、对象版本、处理记录、复检与有效状态 |
| MissingInfoRequest | 缺什么、要求依据、影响对象、可接受材料、阻断范围、处理状态 |
| DependencyEdge | 上游具体版本、下游具体版本、关系类型；区分实际引用与检索范围依赖 |
| Run / Task / Attempt / Event | 阶段、状态、任务键、租约、输入版本、尝试、checkpoint、错误、递增事件序号 |
| ContextManifest / ModelCall | 实际输入引用、必需/可选项、token 估算/实测、模型与提示词版本、用量和费用 |
| TaskContract / ValidationReceipt | 本轮目标、输入指纹、验收规则版本、预期检查项；产物哈希、检查覆盖、结果、依据和判定方 |
| ContextSnapshot | task_id、上下文代次、状态/基线版本、进度、未决问题、原始引用、摘要、压缩校验及取代关系 |
| ExperienceRule | 写作经验、适用范围、来源修改、候选/已确认/作废、确认人 |
| DefectExample | 原稿/改稿版本及定位、缺陷类型、理由、批准状态、适用范围、反例与回归结果；合成与真实样例分开 |
| AgentProfileRevision / CredentialRef | 提供商、模型用途、能力测试、上下文/费用/执行参数、可发送范围；凭据仅存系统凭据库引用 |
| Conversation / Message / ActionRequest | 项目、消息、作用对象/版本、意图、允许动作、幂等键、确认记录和关联任务/产物；对话与执行状态分开 |
| ReleaseManifest | 基线、章节版本集合、审核及渲染记录、未决事项、DOCX/PDF 哈希、放行人与时间 |

DOCX 的块路径不冒充原始页码；渲染映射另存。解析器没有置信值时使用 unknown，不编造置信分数。合并单元格和跨页表格保留关系；人工纠正产生新的解析版本。

### 3.2 必须落实到服务和数据库的约束

1. 同一文档版本内的 SourceBlock 引用稳定；重复上传通过项目绑定幂等，不将其他项目的权限一并共享。
2. 企业事实只有已确认且当前适用的版本可支持硬事实；规划方案可由项目决定支持，不能冒充已有产品能力。
3. 草稿采用不可变版本，当前版本指针更新使用 expected_revision 比对；旧任务不得覆盖人工新稿。
4. 审核绑定正文和上游版本指纹；任一依赖变化后不能继续作为当前通过结论。
5. 同一个 task_key 只允许提交一个正式结果；重放保留调用/尝试记录，但不重复晋升正文。
6. 交付放行在同一业务事务中核对有效性并写清单；随后文件只读。外部修改通过新候选版本重新验收。
7. 一个事务内提交业务版本、依赖、任务结果和失效事件；索引和 checkpoint 随后完成。中途失败由幂等任务重放及对账恢复，不假定跨存储事务自动原子。
8. 每次运行及放行重新计算证据有效期；按招标约定的适用时点校验，未约定时显示所用的拟提交日期。过期不依赖人工再次上传才能发现；日期含义不清时标待核。

## 4. 工作流、上下文与记忆

### 4.1 工作流节点

```text
解析及完整性核对 → 要求/评分台账 → 证据/缺口 → 大纲与小样
                                              ↓
                      章节任务 → 上下文 → 写作 → 章节审核
                         ↑                         ↓
                         └────── 有界修订 ─────────┘
                                              ↓
                          全文审核 → Word/渲染 → 放行候选
                                              ↓
                                          人工放行
```

| 节点 | 输入 → 持久化输出 | 失败/缺口去向 |
|---|---|---|
| parse | 原件版本 → SourceBlock、逐页/对象台账 | 解析异常；人工纠正或重新识别 |
| analyze | 当前原文块 → 要求、评分规则、遗漏复查记录 | 条件/评分不明确进入待核 |
| match | 要求＋企业资料 → 证据关联、缺口 | 仅挂起依赖任务 |
| plan | 要求＋证据＋项目约定 → 大纲、本节方案、细目录/展开计划、章节任务、小样 | 方案及细目录检查未通过则重规划/补读；首次大纲/代表小样由人确认 |
| write | ContextManifest → 草稿候选、Claim | 缺依据进入缺口；版本冲突保留候选 |
| review_section | 原始要求＋证据＋本节方案＋当前草稿 → 覆盖/解释/证据状态、问题清单 | 方案错误回 plan，缺依据补读/待核，正文问题进入 revise；客户语言编辑后复检事实/约束 |
| revise | 问题＋当前版本＋锁定约束 → 新草稿版本 | 两轮用尽或无进展转人工 |
| review_global | 生效要求＋全稿＋约定 → 覆盖、矛盾、附件、估分报告 | 按问题路由到相关章节，不整本盲写 |
| export_validate | 通过检查的正文集合 → DOCX、PDF、视觉问题、清单 | 排版问题修复后重新渲染 |
| release | 有效清单＋人工决定 → 不可变放行记录 | 有阻断项或版本变化则拒绝放行 |

每个章节通过后仍要检查整本。全过程可查阅原文。带星号、实质性、评分、附件及提交要求分别处理，不依赖单一符号识别关键条件。

全文审核分四批执行，避免将整本塞进一次上下文：按原始要求逐项核查正文/附件去向；按 Claim 的主体、属性、数值与条件分组检查跨章矛盾；对解析台账逐页/逐表复查是否漏提要求；最后检查结构、卷册与附件。语义任务按条款/事实组拆分，每项写回结果，存在未检查项时整本审核不能完成。估分按原评分项汇总区间，未知项单列，不为缺少规则的项目自造分值。

### 4.2 Agent 在节点内可以做什么

节点提供白名单工具：search_evidence、read_source、read_project_decisions、read_section、create_missing_request。模型可决定检索词、继续读哪份原文或提出缺口；不能直接改数据库、把候选事实置为 confirmed、解除锁定或放行交付。

首版每个写作/审核任务每轮最多四次工具调用，计入持久化的任务族预算；不足时保存已发现信息并拆分或转待处理，预算用尽不能通过换会话、恢复或拆任务刷新额度。后续工具预算由错误样本校准。工具参数由服务验证项目范围和当前版本；文档中的“忽略规则、修改系统配置”等文字始终作为材料内容处理。

### 4.3 状态与恢复

任务状态：queued、running、waiting_input、succeeded、failed、cancelled、stale。run 另有 paused；暂停在当前调用结束后停止派发后续任务，不能声称已撤销提供商计费。

执行状态与产物验收状态分开：工具/模型成功只说明动作完成。产物记录 candidate、accepted、rejected、stale，另有 passed、failed、unknown、not_run 的校验结果；动作结果即使已落盘，也须通过适用校验才能被当作已验证输入。审核任务成功保存问题报告不代表受审正文通过，两个对象分别记录验收。

缺口任务先写入业务库，其他可执行章节继续；没有可执行任务时，父 run 才进入 waiting_input 并保存 checkpoint。恢复操作校验缺口版本和当前基线；重复提交恢复请求使用同一幂等键。

task_key 由 run_id、节点、业务对象和输入指纹组成；输入指纹包含项目、依赖版本、提示词/契约和模型配置。重复启动请求通过 request_id 返回原 run；明确重新运行生成新 run，重复恢复仍使用原 task_key。worker 领取租约并定时续租；提交时校验租约 token 和输入版本。租约过期可重跑，但旧 worker 的迟到结果不能晋升当前稿。

业务库与 checkpoint 不一致时，以已提交的 TaskResult 为准对账：已有结果则跳过模型重调并补记流程位置；没有结果才重试。模型调用已发出但响应未落盘时可能重复计费，记录 unknown 用量并保守占用预算，不能承诺模型接口 exactly-once。

### 4.4 上下文装配规则

顺序固定：范围过滤 → 生效版本/产品/有效期过滤 → 明确引用直接读取 → 关键词与向量召回 → 结果融合 → 补齐表头、父标题和必要相邻块 → 按预算装配 → 保存 ContextManifest。

- 必需项：任务要求、当前条款及条件、必须遵守的项目决定、修订问题、锁定内容。必需项超预算则拆任务。
- 证据项：覆盖本任务事实的有效原文；支持关系未确认的材料不能作为已证实事实。
- 写作设计项：当前已验收 SectionDesignRevision、细目录及必须展开的问题；按章节类型加载少量已批准好坏样例，不带入旧客户事实。设计版本变化使关联正文/审核按依赖重判。
- 可选项：历史写法、低相关材料、前文摘要。按相关性缩减并记录原因。
- 初始检索参数：关键词/向量各召回 30 条，以 RRF 融合；初选八个证据块，再按要求覆盖补读。直接指定的条款不受 top-k 限制。
- 初始输入目标 24k token；同时预留输出、工具返回及提供商要求的推理预算，不超过模型总窗口。实际值由 pilot-profile 配置，不把字符数当精确 token。
- 索引记录 embedding 模型、维度、切块和分词版本；更换配置重建命名空间，不混用向量。
- 审核输入独立装配，不接收写作者“已满足”的自评；逐页/逐表抽取复查用于发现共同漏项。

ContextManifest 至少包含 task_id、baseline_id、required_refs、evidence_refs、decision_refs、draft_refs、issue_refs、experience_refs、omitted_refs、token_estimate、实际输入哈希。任何材料缺口不能被裁剪日志掩盖。

具体拆分、压缩和跨窗口恢复采用第 4.7 节协议；每次模型/工具请求前都检查预算，不能等提供商返回超限才开始处理。

### 4.5 补遗与新增资料

变更确认后写新版本和失效事件，沿 DependencyEdge 找到相关正文、Claim、审核和交付候选。资料新建而不是替换也可能改变原结论：额外记录项目/产品/主题的检索范围版本，触发受影响的检索和缺口重判。

M1—M2 先使用保守规则：当前项目基线改变即停止旧结果晋升，并要求重新核验交付。M3 再缩小到可靠的影响范围；无法确认边界时仍扩大复核，不为减少重写而遗漏依赖。

经验从人工修改记录提炼为 candidate，用户选择项目/企业/通用范围后生效。首版支持查询、确认、作废和来源回查，不做自动跨项目学习。

知识库由独立入口初始化并发布，项目选择已发布的产品/知识版本。后续发布新知识版本只生成更新提示和影响分析；用户确认采用后建立新项目基线，旧审核才按依赖失效。证据到期仍按适用时点主动检查，不因锁定版本继续把过期资料视为有效。

### 4.6 统一 Do—Check—Loop 协议

1. **建立契约**：TaskContract 固定本轮目标、企业/项目、父任务、输入版本、产物格式、必查项、语义判据、允许动作、预算及检查规则版本。首次大纲/小样和最终交付保留人工确认，其余按既定契约自动检查。
2. **Do**：程序或模型执行解析、检索、写作、修订、压缩或渲染；保存候选、调用记录、ContextManifest 与输入指纹，不直接晋升有效正文或确认事实。
3. **Check**：程序核对格式、引用、范围、版本和数量；模型核对语义支持与响应；适用的人工事项单独列出。ValidationReceipt 记录 expected_items、checked_items、unresolved_items、issues、verdict、actor/tool/model、规则与产物版本。检查缺失、异常或不确定不得记为通过。
4. **选择动作**：通过则提交适用的验收记录并派发下一步；失败按第 4.9 节路由。上游待核产物仅允许作为明确标注的诊断输入，不作为写作硬事实或已验收依据。
5. **提交与循环**：校验输入仍有效、目标问题已复检、没有新增阻断、锁定内容未损坏，再提交有效版本和依赖；否则保留候选与原因。旧可靠版本保留；相关缺口不影响独立任务执行。

expected_items 由当前输入台账及版本化规则确定，不由写作者自行删减；checked_items 必须属于预期集合，每项记录通过/失败/待核。预期集合中尚未检查的项，以及已检查仍待核的项，都进入 unresolved_items。必查项未完成或待核时不得通过；完整性还须回查原始页/对象台账，不能只对模型已提取的清单计数。

循环有四个范围：工具循环获取证据；节级循环修正局部正文；整本循环发现遗漏和跨章问题后重开受影响子任务；文件循环修复装配与排版后重渲染。节级通过不代表章节通过，所有章节通过也不能替代全文及文件验收。

自动修订初始每节最多两轮，独立拆分的小节共享该节的修订额度。检索、压缩、复检、网络重试分别记账，全部计入项目总预算。达到轮数/工具/费用限制、重复出现同一问题且无有效动作、用户暂停/取消或不可恢复错误时退出；退出为待处理、暂停、失败或取消，不能记为验收通过。新预算须由用户明确调整，不能由模型自增。

### 4.7 长任务、分节与受控上下文压缩

**分工固定**：父工作流只持有任务依赖、阶段、有效产物 ID、缺口、验收记录和预算；正文/原件保存在业务库与文件存储。父工作流可调用规划模型处理高层摘要与约定，模型会话不连续承载整本历史。checkpointer 保存可恢复引用与小状态，不积累整本聊天。LangGraph 的执行检查点与跨线程数据分工见 S1；摘要、笔记和按需读取的实践依据见 S9。

**拆分粒度**：大纲的“节”是默认写作与验收单位。按本节要求、证据和预计输出预算拆成完整条款组/业务场景；不能按固定字数机械切开条件、表头与数据。每个子任务有明确 coverage_ids；父节合并时核对所有 coverage_ids 和子任务结果，补查衔接、重复及矛盾。必需约定仍超预算时缩小本轮目标，不能对硬条件做有损摘要后继续。

每次新子任务或新修订轮次，从当前数据库重建上下文，不携带其他章节完整对话。上下文包含：本轮契约、对应条款及条件、相关证据原文、已确认项目约定、必要的前置章节承诺、当前正文/锁定块、未决问题、有限参考。跨节承诺保存在 Claim/Decision，不能只靠滚动摘要传递。

**三种摘要分别管理**：

| 摘要 | 生成来源及用途 | 必须校验 |
|---|---|---|
| 资料/章节导航摘要 | 原始结构块或已验收正文；供检索和理解前文 | 来源版本、关键内容引用；不能作为事实支持原文的替代 |
| 项目状态视图 | 数据库内已确认决定、术语、关键承诺和待办；供跨节共享 | 结构化投影为主；数值、单位、条件、确认状态和范围与原记录一致 |
| 执行交接摘要 | 本子任务的动作记录、结果 ID、问题和下一步；供换窗口/恢复 | 已做与待做分开；无进度虚报，无关键问题/锁定引用丢失 |

摘要引用源对象和具体版本，使用状态为 candidate/validated/stale。源版本或相关决定改变时失效；导航摘要可以不穷尽所有原文，但不能独占检索入口。摘要不是新的企业证据，待确认不能压成已确认，否定/例外不得反转；摘要缓存不能改变项目知识基线。

**预算与触发**：令 C 为配置并验证的模型总窗口，O 为输出预算，R 为提供商适用的推理预留，S 为安全余量，得到可用输入 B=min(任务输入预算, C−O−R−S)。配置须按提供商实际计数方式校验，避免重复扣除推理额度；图片/表格视觉输入也纳入预算。24k 只是初始任务输入目标。下轮现有输入加预计工具结果超过 B 的 80% 时开始清理/交接；真正发送前必须确保总输入不超过 B。80% 为可配置起点，不是模型性能保证。

**压缩顺序**：先去重复工具结果及无关写法 → 工具大结果落盘并保留有定位的摘录 → 从权威状态重建相关约定 → 对仍需保留的执行历史生成交接摘要 → 校验快照并换窗口。始终保留或按当前任务重新读取条款原文、证据、数值/单位/条件、锁定内容和未决问题。仍装不下则继续拆任务，不删除必查项，不因固定 top-k 停止必要补读。

**压缩也是受检步骤**：ContextSnapshot 保存 task_id、context_epoch、baseline/input fingerprint、task_contract_ref、accepted_output_refs、open_issue_refs、next_action、source_refs、summary_text、validation_receipt_ref。程序从结构化状态确定必须保留的 ID 与字段，逐项比对并检查范围/版本/可回读性；摘要中的实质性表述须有来源并做语义复核。不能通过只比较摘要自身得出“无丢失”。

校验通过才切换新窗口；失败保留旧快照，重新生成一次，仍失败则拆任务或转待处理，不无限摘要。每次从原始动作记录和当前业务状态生成快照，禁止只用上一次自由文本摘要递归压缩。新窗口先核对版本、租约、预算和已有 TaskResult，再恢复下一动作；摘要不携带模型隐含推理，不依赖不可访问的内部状态。

工具调用尚未结束时先等待或记录 attempt 为未决，不在压缩时声称已完成；恢复后按幂等键对账。已完成请求/响应成对归档，通过新构建的合法请求继续，避免裁剪出悬空工具调用。压缩、拆分或更换上下文均不重置修订次数、费用或原始任务身份。

### 4.8 各阶段产出、校验与失败去向

本表是运行时验收，区别于 P01—P16 的工程交付验收。每行均保存 ValidationReceipt；语义判断不能用“格式合法”代替，模型报告本身还须校验引用和检查范围。校验器由合成缺陷与人工样本校准，不递归无限自审。

| 步骤 | 必须产出 | 校验内容/方式 | 未通过时 |
|---|---|---|---|
| 知识库初始化/更新 | 原件、结构块、事实候选、索引、发布版本 | 程序查版本/范围/索引配置；语义查支持关系；人工确认新增关键事实 | 未核材料保留候选，修正后发布；不反复索要已有有效材料 |
| 项目创建与选库 | 项目范围、知识版本、提交时点及基线 | 程序查版本可用、企业/产品范围；人工确认项目特殊约定 | 纠正选库/范围，不默认套最新版本 |
| 招标解析 | 正文/表格/图片块、逐页/对象台账 | 程序检查处理覆盖与定位；图文核对及人工复查异常/关键页面 | 重解析或人工纠正；未知页不能消失在分母中 |
| 要求与评分抽取 | 条款、条件、评分规则及原文映射 | 程序验证引用；语义与原始页/表逐项对照；人工核对关键提取基准 | 补抽、纠正或待核，不凭抽取清单自证完整 |
| 证据匹配 | 要求—证据关联、支持判断、缺口 | 版本/有效期程序校验，原文语义核对；检索无结果不等于企业不具备 | 补检索、核验或请求缺失信息 |
| 大纲与写前设计 | 大纲、coverage_ids、依赖、本节方案、细目录/展开计划、小样与任务契约 | 映射/依赖程序核对；按章节类型检查方案机制/来源、细目录业务一致性；人工确认大纲/代表小样；超范围责任有去向 | 设计错误重规划，缺依据补读/待核；不靠换措辞或增加标题过关 |
| 上下文组装 | ContextManifest、实际输入及哈希 | 程序查必需项、来源/版本、预算和锁定引用；复核证据条件完整性 | 补读、重建或拆分，不静默截断 |
| 压缩与交接 | ContextSnapshot、原始记录引用、交接摘要 | 第 4.7 节的字段、状态、原文支持、版本、预算与回读检查 | 重建一次；仍失败拆分/待处理，不切换到失真快照 |
| 分节写作与合并 | 草稿块、Claim、依据、未决项与子节覆盖清单 | 格式/引用/锁定程序核对；语义分开查覆盖、解释深度、证据支持与正负约束；合并查衔接/重复/矛盾 | 局部修订、补证据或重规划；暂不晋升已验收稿 |
| 客户语言编辑 | 面向客户的正文候选、差异及复检记录 | 检查作者说明、空泛修辞、翻译腔；保留真实否定/条件/范围；复检语义、承诺和限制变动 | 表达问题局部改写，语义变动回对应核验；不复制内部设计字段到正式稿 |
| 章节/整本审核 | 对照表、逐项结果、问题、估分与未检清单 | 检查集合等于预期集合；独立核对原始要求、跨章承诺及附件；报告与正文分开判定 | 重开相关任务；unknown/not_run 不登记为满足 |
| 修订与复检 | 新候选、差异、目标问题及回归结果 | 目标问题解决，无新阻断，输入仍有效、锁定保留；相关要求重新核验 | 拒绝晋升并保留旧可靠版；次数耗尽转人工 |
| Word 装配与渲染 | 最终 DOCX、对应 PDF/页面图、文件检查记录 | 程序查资源/编号/哈希；全页视觉检查；目录更新后以最终文件验收 | 修内容/模板/装配后重渲染，不能用渲染成功冒充版式通过 |
| 最终交付 | ReleaseManifest、响应矩阵、审核报告及人工决定 | 程序查全链路当前有效、阻断/关键待核为零、重要项处置、文件哈希；人工最终确认 | 仅允许标明未验收的草稿导出，不授予放行状态 |

### 4.9 质量损失、修复路由与采用条件

TaskContract 关联质量规则版本。先判硬门槛（实质性要求、事实/承诺、卷册/项目、文件可用性、版本），状态为满足/不满足/待核。只有硬门槛满足的候选才比较质量损失：响应、非阻断事实缺陷、一致性、方案具体性、表达/排版五项分别归一化并按已确认权重汇总。招标分值优先决定响应权重，未知项单列；没有适用评分规则时只输出缺陷和待核，不生成貌似精确的总分。

Loss 用于优先级和候选比较，不参与首版模型训练，也不单独决定放行。改善不得来自删条款、改验收门槛、把待核写成满足或缩小检查集合；评审规则调整须新建版本并重新评估，不能直接与旧分数比较。

纠正动作由问题原因决定：漏读→重解析；漏提→补抽要求；召回不足→重检索；版本/摘要错误→重建上下文；事实缺失→补材料/确认；正文错误→定向修订；跨章冲突→先核对项目决定再改相关章节；文件问题→修装配并重渲染。每轮记录问题增减、实际动作、产物差异、消耗和下一步，不因 Loss 降低自动提交。

内容质量细则见[内容质量与写前设计](标书Agent内容质量与写前设计-v0.1.md)：写前方案未成立退回规划；细目录拼点退回结构设计；“提到了但未解释”按必须回答的问题补写；正负两类无依据约束均需处置；语言编辑后重新检查条件和范围。审核不以篇幅、关键词或笼统自评分证明深度，不能为了写具体而虚构能力或新增要求。

章节、整本和文件的“完成”均要求适用检查有当前版本的通过记录；人工负责关键事实/决定、首次方案及最终放行，不要求每个正常子任务都等人点击。长任务因缺信息/预算/失败停止与最终交付成功是不同出口。

| 项目 | POST /projects；GET /projects/{id}；POST /projects/{id}/baselines | 项目范围在服务端绑定；基线有版本 |
| 资料 | POST /projects/{id}/documents；POST /documents/{id}/parse；GET /documents/{id}/blocks | 上传幂等；原文定位与解析异常可读 |
| 要求 | GET /projects/{id}/requirements；PATCH /requirements/{id}；POST /projects/{id}/requirements/extract | 人工校正使用 expected_revision，评分/条件保留原文 |
| 事实/决定 | GET/POST /projects/{id}/facts；POST /facts/{id}/confirm；GET/POST /projects/{id}/decisions；POST /decisions/{id}/confirm | 确认必须是用户动作，可批量确认带来源的候选事实 |
| 检索 | POST /projects/{id}/evidence/search | 返回来源、范围、版本、匹配原因，不直接返回“已满足” |
| 大纲 | POST /projects/{id}/outlines；POST /outlines/{id}/confirm | 保存要求映射；首次大纲和小样确认关联具体版本 |
| 本节方案 | GET/POST /sections/{id}/designs；POST /section-designs/{id}/validate；GET /sections/{id}/response-assessments | 设计/细目录版本化并绑定验收；覆盖/解释/证据状态分别返回；修改设计触发关联结果复核 |
| 章节 | GET /sections/{id}；POST /sections/{id}/drafts；POST /sections/{id}/generate；POST /sections/{id}/locks | 正文按块编辑；expected_revision 冲突返回 409 |
| 缺口 | GET /projects/{id}/missing-requests；POST /missing-requests/{id}/resolve | 补件触发复核，不直接把要求置为满足 |
| 执行 | POST /projects/{id}/runs；POST /runs/{id}/{pause,resume,cancel}；GET /runs/{id}/events | 所有写操作含 request_id；只恢复当前允许的动作 |
| 验收/上下文 | GET /tasks/{id}；GET /tasks/{id}/validations；GET /tasks/{id}/context-snapshots | 展示契约、候选/验收状态、检查覆盖、失败去向、预算与上下文代次；摘要可回查来源 |
| 审核 | POST /sections/{id}/reviews；POST /projects/{id}/reviews；POST /issues/{id}/resolve | 问题处理与复检分开；旧版本报告不可放行新稿 |
| 变更/经验 | POST /projects/{id}/changes；POST /changes/{id}/confirm；GET/POST /projects/{id}/experiences；POST /experiences/{id}/{confirm,revoke} | 变更先预览影响再生效；经验确认时指定适用范围 |
| 交付 | POST /projects/{id}/exports；GET /exports/{id}；POST /exports/{id}/release | 核对有效审核、渲染、哈希及人工决定 |

全局入口：项目、产品与知识库、记忆中心、设置。项目内部含概览、资料/原文、要求矩阵、大纲与块编辑、缺口/问题、运行验收、交付；常驻助手可关联当前对象，正文占主要空间，原文对照复用工作区/抽屉。设置包括模型连接/用途、执行策略、存储备份；记忆中心管理项目决定与表达经验，企业事实链接知识库。各模块最小页面随对应后端任务完成，P14 统一联调。

具体交互与消息/动作契约见[交互与课程对照](标书Agent交互与课程对照-v0.1.md)。对话是意图入口，业务状态由数据库与验收服务决定；模型回复不能直接确认事实、改变项目范围或宣告放行。后台运行时查询单独执行，变更在安全提交点协调；不把全部聊天历史连续作为模型输入。设计参考 S10/S11 的拆解、工具、反馈与评估原则，三栏布局和具体确认规则是本项目选择，尚待界面验证。

## 6. 开发任务

### 7.2 必测故障与不变量

| 故障/输入 | 断言 |

| 表格要求被解析器漏读 | 完整性/人工基准复查暴露缺口，不能声称覆盖完整 |

### 12.3 候选必须遵守的业务边界

1. **父业务任务与节内循环分开**：数据库 worker/租约/依赖/契约仍控制全流程；Harness 只负责当前节或审核任务的模型/工具活动。运行完成只产候选，验收服务决定后续动作。
2. **独立上下文**：每个节/条款组、独立审核从业务状态装配输入；前端 Conversation 不等于底层执行 session。任务、attempt、session、配置、基线和预算显式关联。
3. **受控压缩**：替换默认编程摘要；从原记录与当前状态生成并校验快照。默认自动压缩失败可能继续运行，必须另设实际请求前阻断，不能仅以摘要抛错作为保证。
4. **工具与权限**：专用 profile 白名单、最终拒绝 guard、后端范围/版本校验三者同时落实；用户聊天先形成 ActionRequest，不直接透传为 runtime 原生命令。
5. **实际请求预算**：写作、审核、摘要、格式纠正、溢出恢复和网络重试均记账。一个业务任务只由一层管理重试；无法证明隐藏请求受控则不采用。
6. **知识和记忆归业务库**：KnowledgeBaseRevision、Fact、Decision、ExperienceRule、DefectExample 按原契约管理，运行会话及摘要不能成为新的能力事实。
7. **设置与交付**：用途模型/摘要模型、数据范围和凭据配置固定到本次运行；Word 仍从统一内容块生成并验收，不因 Harness 自带 Office API 而直接替换已定交付链。

### 12.5 采用与退出判据

- 工程门：H01—H03 均通过。接口存在或替身通过不能替代真实提供商与故障测试。
