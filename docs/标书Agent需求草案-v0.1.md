# 独立标书 Agent 需求草案 v0.1

历史草案。当前实施计划采用的需求基线见：[需求规格 v0.2](标书Agent需求规格-v0.2.md)。

日期：2026-11-12。

状态：用于独立 Agent 试点的需求草案。产品方向来自当前讨论；首版使用范围、样本规模和量化目标是建议默认值，尚未视为用户逐项确认。本文不代表已经开发或通过验收。

关联研究：[整体方案评估](../research/标书Agent整体方案评估-2026-11-12.md)。

## 1. 产品定义与目标

建设接入大模型的独立标书应用，围绕一个投标项目组织资料、要求、任务、正文和审核，持续完成从材料准备到可验收交付的工作。

核心用户价值：减少逐步骤指挥、反复提供上下文、查证和返工的人工时间，同时保持要求覆盖、事实可靠与交付可追溯。

完整闭环定义：每项要求都有去向，每项关键事实与承诺都有依据，每个问题都有处理结果；缺资料能够补充后恢复，资料或正文变更能够触发复核，最终交付与已验收版本一致。

## 2. 已明确的方向与首版假设

### 2.1 当前已明确的方向

- 优先尝试独立标书 Agent，并接入大模型。
- 覆盖知识准备、招标理解、规划、写作、审核、修订和交付的完整业务流程。
- 上下文与记忆组织是核心能力，支持长文、多步骤和跨会话工作。
- 支持中途补充信息，参考历史优秀标书，进行章节和全文审核。
- 用实际验收与人工工作量衡量收益，与 Codex＋Skill 进行对照。

### 2.2 首版建议默认值，可调整

| 事项 | 建议默认值 | 需保留的边界 |
|---|---|---|
| 用户与企业 | 单人、单企业 | 数据结构保留企业与项目范围，不先做商业化租户体系 |
| 运行方式 | 本地或单实例服务，专用操作界面 | 不预先限定桌面应用或 Web 技术栈 |
| 首个场景 | 中文技术标 | 仍识别全项目资格、商务与附件条件；只对约定卷册负责成稿 |
| 项目管理 | 可保存、切换多个项目 | 首版不要求同时并发制作多本标书 |
| 输入 | DOCX、文字型 PDF、扫描 PDF/图片 | 产品、资质、案例、历史标书均可导入；其他格式按真实样本扩展 |
| 输出 | 可编辑 DOCX，预览 PDF，单独的响应矩阵与审核报告 | 不把内部证据标记或诊断内容混入正式正文 |
| 模型 | 首个真实模型接口跑通，模型配置可替换 | 不要求首版同时支持多提供商或多 Agent |
| 人工介入 | 确认关键事实、承诺、大纲与最终交付 | 在约定范围内自动推进，按缺口和风险集中请求信息 |

行业、企业产品、专有术语、模板和章节顺序由项目配置与原始材料决定，不默认继承现有 Skill 的 DHR 场景。

## 3. 用户操作与主流程

用户创建项目，选择交付范围，导入招标文件、补遗和企业资料。Agent 形成可回查的要求台账，检索并关联证据，列出缺口；再提出大纲和写作小样，按确认范围逐节写作，完成章节及全文审核，修订复检，生成和检查交付文件。

用户可以查看进度、查证原文、补资料、调整大纲、修改或锁定正文、处理审核问题、暂停恢复和导出候选稿。Agent 自动继续不依赖缺失资料的任务。

大纲或小样出现重大范围变更时再请求确认；沿用已确认约定时不重复询问。未决问题只阻断有依赖的工作，是否阻断整本交付须明确说明。

## 4. 首版必需功能及验收标准

| 编号 | 需求 | 可观察的验收条件 |
|---|---|---|
| F01 | 创建项目及交付范围 | 项目记录客户、卷册、目标产物与当前基线；切换项目后不带入其他项目的私有内容 |
| F02 | 资料导入、分类和版本管理 | 保留原件、来源、版本和处理状态；同名文件不默认为同一版本，重复导入可识别 |
| F03 | 文档结构读取与异常处理 | 正文、表格和图像具有原文定位；失败或低置信页面单独列出，不能用成功页掩盖漏读 |
| F04 | 招标要求及评分规则提取 | 每项记录原文、条件、适用范围、分值或评价口径；用户可校正，评分表关联不丢失 |
| F05 | 企业知识整理与检索 | 区分产品事实、资质、案例和方法参考；证据含版本、适用条件和确认状态，能打开原文 |
| F06 | 明确写作任务与大纲 | 每项要求映射章节、附件或当前卷册外责任；每节明确写什么、依据什么、依赖什么、缺什么 |
| F07 | 分节写作及历史样本参考 | 根据当前要求和有效证据生成；借鉴表达不迁移其他项目身份和未经核验的事实；正文逐节保存 |
| F08 | 补资料与恢复 | 缺口说明所缺内容、依据、影响及阻断范围；补充后更新相关任务并继续，找不到资料不直接判定企业不具备 |
| F09 | 章节审核与有界修订 | 问题给出依据、位置、严重度及复检条件；修订形成新版本，超出轮数/费用限制时停止并说明原因 |
| F10 | 全文审核与估分 | 复查原始要求、跨章承诺、附件与串稿；按评分项输出估分依据、区间和未知项，不称为实际得分 |
| F11 | 变更影响与失效重审 | 补遗、事实、决定或草稿改变后，关联章节、问题结论和交付候选标记待复核；无关章节无需全部重写 |
| F12 | 人工编辑保护 | 人工修改产生版本；锁定内容不被自动覆盖，生成期间出现并发编辑时保留候选并显示冲突 |
| F13 | 中断恢复与执行控制 | 重启后恢复已提交成果和待办；重复恢复不重复提交成果，失败可定位到任务；能暂停或取消后续工作 |
| F14 | Word 装配与视觉验收 | 当前章节组成完整文件；表格、图片、目录和分页实际渲染检查，记录检查范围及遗留问题 |
| F15 | 交付状态与版本核对 | 区分工作草稿、候选稿和已放行交付；有阻断项时可导出标明未验收的草稿，不能登记为通过 |
| F16 | 过程、费用与验收记录 | 可查看任务进度、所用资料版本、模型配置、token、费用与失败原因；估算费用与实际用量分开 |

## 5. 上下文与记忆专项需求

### 5.1 保存什么

| 类别 | 内容及使用限制 |
|---|---|
| 原始证据 | 文件、结构块、图像和定位；摘要用于导航，关键事实回查原文 |
| 企业知识 | 已核验产品、资质、案例等；按企业、版本、有效期和适用条件使用 |
| 项目事实与决定 | 本项目范围、术语、架构、工期、服务期和已确认承诺；记录确认来源 |
| 工作状态 | 要求、章节、依赖、待办、审核问题与执行位置；可以从持久化成果恢复 |
| 草稿与交付 | 正文版本、人工修改和审核记录；不能自动成为新的企业事实 |
| 写作经验 | 人工修订原因、表达偏好、错误模式；带适用范围，经核验后推广 |

模型推测、待确认信息、正式事实和已作废结论必须区分。项目经验不自动跨项目共享，历史标书中的承诺不自动升级为本企业当前能力。

### 5.2 每次任务加载什么

每次抽取、写作或审核，根据任务选取当前生效的原始要求、必要证据、相关项目约定、依赖章节信息和未决问题；记录实际加载的内容、版本及省略原因。

不得依赖整段聊天作为唯一记忆。上下文不足时拆任务或继续定向读取，不静默截断关键条款；不以固定召回三条或读完整本作为所有任务的规则。

章节可以在全新模型会话中恢复工作，且仍使用正确的事实、术语和版本。全文审核可以从原始招标文件回查，不能仅复用写作时的同一份摘要。

### 5.3 变更与纠错

修正一个事实时保留旧版本与取代原因，并找到其关联的正文和审核。即使项目已经完成，重新打开或重新导出也要检查相关资料是否更新或失效；历史交付保留其当时的验收记录。

## 6. 审核、人机分工与交付规则

- Agent 负责组织流程、查材料、写草稿、发现问题、修订和复检；用户负责无法由材料推导的事实与商业决定、关键承诺和最终放行。
- 用户不需要逐节给操作指令；需要补充或决定时，问题必须具体并尽量集中。
- 每个要求区分“材料缺失”“未响应”“无法判断”“不满足”“待核”和“已验证响应”；超出当前卷册仍须记录去向。
- 每条关键事实/承诺应关联企业证据、经确认的项目决定或明确的适用条件；引用存在与实际支持该承诺要分别检查。
- 发现阻断问题时停止交付放行。重要问题要处理或明确记录人工接受的风险；不能通过总分抵消关键缺陷。
- 持续修订没有进展、缺乏依据、达到费用或轮数上限时进入待人工处理状态，保留最后可靠版本。
- 放行绑定原始要求基线、章节版本、审核结果和导出文件；任一相关版本变化都需要重新判断受影响的验收。
- 人工放行不代表法律或投标结果保证；系统呈现待核内容，不宣称自动保证中标或零错误。

## 7. 代表性端到端验收场景

下列场景应先准备输入与人工基准，再检验完整流程，不只测试生成文本。

| 场景 | 必须观察到的结果 |
|---|---|
| T01：正常成稿 | 从资料入库到 Word 和报告完整走通；逐项要求可定位正文或附件 |
| T02：要求在表格或扫描页中 | 正确读出条款及条件；无法识别时暴露异常并阻断受影响的合格结论 |
| T03：关键材料缺失 | 不编造证书或案例；生成明确缺口，其他任务继续；补齐后恢复 |
| T04：历史标书含其他客户及旧承诺 | 可以参考写法，但不能串入身份、旧工期和未经核验的能力 |
| T05：存在多个产品或证书版本 | 使用适用版本；版本冲突或证书过期时产生可定位问题 |
| T06：写作中收到补遗，服务期三年改五年 | 找到受影响的正文、计划和附件，旧审核失效；修订后重新核验 |
| T07：前文单中心，后文同城双活 | 检出关键矛盾，回到项目约定处理，不自行合并成模糊措辞 |
| T08：用户修改并锁定段落 | 后续自动修订保留锁定内容；若与新要求冲突，显示问题等待处理 |
| T09：生成中断、重启、重复恢复 | 已提交成果保留，未完成任务可续作，不产生重复提交或错误版本 |
| T10：已有审核通过，随后正文改变 | 旧结论不能给新正文放行；新导出文件与新审核版本匹配 |
| T11：项目切换 | 不召回或使用其他项目的受限事实、客户和草稿 |
| T12：模型失败、预算耗尽或反复修订无效 | 停止受影响任务并说明原因，可恢复；不能伪报完成 |
| T13：正文有图片和复杂表格 | Word 和预览可读，检查图片、表格、目录和分页；明确抽检与未检范围 |

## 8. 如何判断试点值得继续

比较三组：当前 Codex＋Skill、增强版 Codex＋Skill、独立标书 Agent。使用相同材料快照与交付目标，记录模型差异、人工介入、运行费用和失败；对正文质量采用隐藏方案名称的人工评审。

首要指标：达到同等验收标准所需的人工处理时间。同步记录关键要求遗漏、无依据承诺、跨章矛盾、审核漏报、变化后的恢复与复检、最终文件质量及总成本。

建议试点目标：关键风险不劣于增强版 Codex＋Skill，人工处理时间中位数降低至少 30%。这个比例尚未由用户确认，也不是收益承诺，应在初始基线建立后校准。重大缺陷不能被平均得分掩盖。

样本准备建议：一个真实项目先做少量章节的完整闭环；再扩展到至少一个整本交付和一个独立验收项目。合成缺陷用于测试错误发现，不能替代真实业务材料的验收。

## 9. 试点边界与待定事项

首版以“完整流程、有限使用场景”为原则。多用户协作、复杂权限、自动报价决策、电子签章、投标平台提交、广泛行业模板和自动训练模型，列为后续范围。

需要进一步依据真实材料明确的事项：

1. 首个行业、产品与卷册，以及一本标书通常包含的文件、页数和复杂对象。
2. 可用的企业资料、历史标书、模板与哪些人员可以确认承诺和评审正文。
3. 首个模型接口、资料允许发送到哪里、每项目预算及失败时的处理方式。
4. 本地还是服务化部署、实际使用人员和交付编辑习惯。
5. 试点验收样本与人工工作量基线。

上述事项允许在需求与样本准备阶段逐项落实，不把建议默认值当成已经确认的用户要求。

## 10. 需求到实施的交接产物

- 一份真实项目材料清单与当前唯一基线。
- 人工核对的要求、证据和关键承诺样本。
- 核心业务对象及其版本、依赖、确认和失效规则。
- 按本草案编号组织的端到端验收用例。
- 首个完整流程的实施计划及模型接入配置。

当前目录只有规则、辅助脚本和研究报告，尚未提供业务验收样本。本次仅明确需求，没有开始系统实现或调用业务模型。
