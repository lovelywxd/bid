# 标书 Agent 内容质量与写前设计 v0.1

日期：2026-11-12。状态：根据用户实际使用反馈补充的设计，尚未用真实稿件验证效果。配套：[需求规格](标书Agent需求规格-v0.2.md)、[实施计划](标书Agent实施计划-v0.1.md)。

## 1. 要解决的业务失败

用户反馈：粗看目录和覆盖似乎已完成，细读则泛泛、拼点、缺少展开、作者说明和翻译腔明显，或出现多余且不明确的能力限制；反复提醒后新项目仍重现。尚未取得对应正文与运行记录，不能据此断定具体调用、模型或检索故障。

现有 Skill 已有客户口径、逐点展开、避免模板腔等文本约束。新应用的价值必须由执行门、可检查的写前设计及重复评估证明；换成独立 Agent、多角色或更强模型都不是质量改善的证据。下面的方法也可以用于增强 Codex＋Skill，仍须公平对照。

## 2. 写前必须形成什么

固定流程：原始要求/客户背景/有效资料 → 本节方案设计 → 细目录与展开计划 → 代表小样 → 正文 → 逐点深度及承诺核验 → 客户语言编辑 → 受影响事实复检。方案不成立返回设计；资料不足返回检索/缺口；只有表达问题才进入润色。

每节保存 SectionDesignRevision，包含下表适用项及依据；不保存模型私有推理或要求输出长篇思维过程。分析、规划、写作可以多轮完成，每轮产出须可检查。

| 内容 | 要回答的问题 |
|---|---|
| 客户目标与业务场景 | 谁在什么情况下要完成什么工作，当前需要解决什么问题？背景无依据时标待核，不编造客户痛点 |
| 本节的解决思路 | 采用怎样的组织方式/业务机制，为什么适合已知需求？与总体方案有哪些依赖？ |
| 已知能力与方案选择 | 哪些是已确认现有能力，哪些是项目配置、实施安排或待决方案？每项依据是什么？ |
| 运行过程与关键规则 | 适用的触发、参与人、输入、操作、规则、输出与异常处理是什么？哪些细节影响客户判断？ |
| 细目录与展开计划 | 每个标题回答哪个完整业务问题，各响应点放在哪里，哪些无需另起标题？ |
| 证据与待决项 | 哪些表述有来源支持，哪些需补证据/决定，哪些只是写法参考？ |
| 承诺与边界 | 是否产生新的功能、数量、时效、人员、客户配合条件、排除项或服务限制？是否必要且有依据？ |

这些字段按内容类型选用：功能方案重业务规则和操作过程，实施方案重活动/职责/交付与依赖，总体方案重选择依据和架构衔接；简单资格条款可能只需证明材料。不要求所有标题机械套用同一套小标题，也不把内部设计字段复制到正式稿。

有资料但未查到时先定向补读；权威资料不存在时承认缺口。设计中标待核的内容不能被写作者扩写成已支持能力。关键决定由用户确认，其他设计按已批准规则自动检查；不要求用户逐节从零代做方案。

## 3. 细目录怎么形成和验收

高层目录遵从招标/评分结构；细层围绕完整业务任务、生命周期或紧密关联的规则组织。评分点是必须覆盖的索引，不要求每点都变成标题。

细目录逐项记录：标题、核心业务问题、适用要求 ID、展开要点、与相邻节的边界、来源/设计引用。检查：同一层级的组织依据是否一致；一个标题是否拼接了没有业务联系的多个点；同一场景是否被过度拆散；是否遗漏条件或重复；标题是否能让客户预期将读到什么。明确规定的招标目录优先保留，内部写作计划另行组织。

例如在“组织管理”下，把“权限、同步、历史、统计”并排凑标题可能混合控制规则、集成机制、数据记录和输出。若原始需求涉及组织调整，可考虑“组织建立与维护”“组织调整的生效与历史查询”“与相关系统的数据衔接”，权限和查询规则放入相关业务过程。此例只说明组织方式，不断言某产品具备这些能力，不作为真实项目目录模板。

## 4. 怎样检查讲清楚，而不奖励篇幅

每项要求分别记录 requirement_presence（未提及/已提及）、explanation（不适用/不足/充分/待核）、evidence（不适用/缺失/支持/冲突/待核），附正文位置、依据和未回答的问题。资格证明、流程说明等采用不同判据；有关键词或章节位置不等于解释充分。

先从要求、已确认设计和领域人工基准确定“本项必须回答的问题”，再检查正文是否回答。审核者不只依赖写作者自己的清单；不得自行添加与投标无关的更高标准。重要业务方案尚有关键未回答问题时，本节不能标成内容已验收。

具体检查包括：客户是否知道实际如何办理/实施；关键规则和责任是否明确；适用条件与输入输出是否连贯；设计选择是否有需求和资料支持；重复口号是否挤占正文；补充细节是否真实且必要。没有要求的异常流程、量化指标或责任承诺，不为凑“深度”强行增加。

反例：“提供灵活的审批能力，提升管理效率。”只能说明目标或功能名；如果条款要求说明审批流程，就要解释适用业务、发起/流转方式、关键规则和处理结果，具体能力必须回查资料。不能仅把“灵活、高效、闭环”各扩写成一段。深度按业务问题是否被回答评价，不按字数、标题数量或专业术语密度评价。

## 5. 客户表述与承诺一起编辑

“本节将从三个维度说明……”等内部写作导语改成具体业务陈述。对“不是 X 而是 Y”等表达检查其是否包含必要、真实的业务区别；纯修辞对比直接改写，必要否定/例外保留，不能只用关键词批量删除。扫描器定位疑点，语义检查和人工样本决定是否有缺陷。

写前和写后都检查正负两类新增内容：无依据保证、随意精确指标，以及无依据限制、排除、客户义务或自设验收条件。Claim 补充 polarity、适用条件、来源类型、必要性与确认状态；事实和业务约束不能只检查数字。

示例：“本方案不涉及历史数据处理，所有异常均须客户自行解决。”若招标、合同或已确认范围没有这些边界，应标记为擅加限制并返回方案核对；不能为了降低承诺风险随便写入。若来源确有责任边界，则准确保留并检查是否构成投标偏离；不能为了文风好看删除真实限制。

无依据但可选的内容可删除；对必须回答的要求不能删掉回答后称已解决，应核验、明确偏离或转待处理。语言编辑不得改变原有数值、条件、范围和能力状态；差异检查发现变动时重新核验。

## 6. 如何防止每次重犯

每个严重缺陷保存 DefectExample：原文定位、问题类型、为什么有问题、所缺业务问题/依据、批准的改稿、适用范围与反例。没有真实稿时使用明确标注的合成缺陷；用户原话是需求反馈，不能冒充真实稿件证据。

类型至少包括：方案不成立、细目录拼点、响应未展开、作者说明/翻译腔、无依据正向承诺、擅加限制。运行时按节类型检索少量相关好坏样例；经确认后才能作为跨项目经验。例子帮助理解标准，不把旧客户事实或整段答案复制进新项目。

审核验证使用成对稿件：同一要求下的“看似覆盖但空泛稿”与“有依据且讲清楚的稿”，另加入更长但重复、更具体但虚构、语言顺滑但删条件的干扰稿。记录缺陷检出与误报；不能只让写作者及同类审核提示互相判绿。最终由业务评审对留出材料核验。

第一版记录粗稿完成与内容验收两个不同状态；前者不显示为标书完成。指标包括首次验收通过情况、专家实质改写范围/时间、重复缺陷、无依据新增内容、漏掉的业务问题。未经人工基准和多项目验证，不声称新 Agent 已消除这些问题。

## 7. 实施优先级与界面

先用少量有代表性的真实章节验证“写前设计—细目录—成稿—审核”的质量收益，再扩大整本生成。测试至少含一个总体方案节、一个详细功能节、一个实施/服务节；实际材料不足时保持业务验收未完成。该质量门放在 M2 扩大写作之前，界面和任务恢复可独立建设，但不能以工程跑通代替内容效果。

工作区增加“本节方案”页签，展示客户问题、解决思路、细目录、关键依据和待决项，用户可纠正并查看影响。响应矩阵同时显示覆盖/展开/证据状态；对话支持“先解释这节准备怎么解决客户问题”“这段没讲清楚怎样执行”，将反馈写入具名问题和设计版本，而不只是追加“写深入些”的聊天提醒。

开发归入现有任务：P01 准备内容缺陷基准；P03 保存设计/展开与缺陷对象；P08 装配设计和相关样例；P09 先验设计/细目录再写正文；P10 深度、正负约束和语言编辑复检；P14 展示设计及内容验收状态；P15/P16 用真实稿及留出项目验证并对照增强版 Codex＋Skill。
