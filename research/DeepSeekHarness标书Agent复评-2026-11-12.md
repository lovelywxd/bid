# 基于 DeepSeek Harness 构建标书 Agent：复评与采用条件

日期：2026-11-12。评估性质：会话复核、官方文档与源码静态审查；未实施接入、未运行真实标书评测。

配套：[实施计划](../docs/标书Agent实施计划-v0.1.md)、[内容质量与写前设计](../docs/标书Agent内容质量与写前设计-v0.1.md)。

## 1. 结论和本次决策

**工程上有可行的接入路径，值得优先验证；目前不能确认标书产出质量得到保证，也不能确认优于增强后的 Codex＋Skill。**

Harness 可以承担模型交互、工具循环、会话记录与恢复、可替换的压缩服务。企业知识、证据支持关系、写前设计、业务长任务、版本一致性、审核与放行仍需专用系统实现。后者才直接针对用户反映的空泛、细目录拼点、展开不足及无依据承诺/限制。

计划调整为先做有明确退出条件的 Harness 验证，不直接宣布替换原 LangGraph 路线。验证期间不同时建设两套完整执行栈；共用业务模型、界面和验收协议，优先验证候选底座。通过真实章节和整本验收后，再将正式技术基线切换为 Harness；失败则保留原路线或缩减自动化范围。

不能承诺任意输入都能自动生成合格标书。可落实的质量保障是：限定已验证范围，阻断事实/实质性要求错误，公开待核与未检项，按当前版本验收，每份交付由业务人员最终放行。评测通过只支持其覆盖的场景。

由此能推断“有接口完成适配”，不能推断“默认配置已经满足业务要求”或“生成内容会更深入”。

## 4. 源码中影响采用的具体问题

### 4.1 默认压缩不能直接用于标书

默认摘要明确面向编程助手，要求英文工程摘要，允许合并已有摘要继续压缩；其结果作为后续会话背景。它没有标书条款、证据状态、待核决定、锁定正文的业务完整性校验。[H6]

本项目继续采用“按节独立任务＋结构化共享状态＋必要时压缩执行历史”。不建立贯穿整本标书的无限聊天。自定义压缩器必须从当前业务记录及原始动作记录生成 ContextSnapshot，必要条款和证据重新读取，禁止只递归压缩上一份自由摘要。摘要始终不能晋升为企业能力证据。

特别需要验证：基础压缩器在 `agent/pre-step` 自动压缩失败时会记录警告并继续当前轮次。[H7] 因而仅覆写 `summarize()` 后抛错不构成业务阻断。需关闭默认自动压缩或替换服务，并在实际模型请求前独立检查有效快照、必需输入及预算；测试必须证实无效快照没有进入后续业务请求。修复仅可按原计划第 4.7 节从权威记录有界重建，不能直接继续原轮次。

### 4.2 最小 profile 不等于受限业务运行环境

`sdk-minimal` 默认提供 shell，采用 `danger-full-access`；独立工作目录并不限制它访问其他可访问路径。[H8]

拟建专用 profile 只注册证据检索、来源读取、项目决定、章节读取和缺口提交等业务工具；不挂载 shell、任意文件写入、插件安装、子 Agent 或权限修改入口。使用最终拒绝 guard，并由后端业务接口再次执行校验。模型提交的内容只能进入候选，不能直接确认事实、解除锁定或放行。

运行进程仅获得任务范围内的接口凭据和候选文件目录，不获得数据库管理凭据或正式交付写权限。实际加载的工具清单和越权执行测试都须验收，不能只检查模型看到的工具名称。

### 4.3 SDK 完成、超时和恢复都有边界

SDK 的 `resume_session()` 恢复会话历史，不恢复 shell/浏览器等外部进程；会话不存在或不兼容时会报错，不应静默创建替代会话。`request_timeout_seconds` 限制协议响应等待，不限制之后的整段活动；客户端超时或观察回调失败不回滚后台工作，也不代表可以直接重试。[H2]

后端必须持有任务租约、调用状态和对账记录。运行输出的 `completed` 只表示运行结束，结果仍是候选。一个会话只派发一个业务执行活动，查询与控制另走通道，避免交叠通知被记到错误任务。

### 4.4 预算必须覆盖真正发出的请求

源码显示模型重试不会重新进行上下文装配或 `agent/pre-step`；摘要还会独立调用 LLM。[H4][H6] 只在每个“步骤开始”扣一次预算会漏掉重试和压缩。

候选实现须在实际模型请求边界预留预算，记录写作、审核、摘要、格式纠正及重试；提供商适配器的内部重试须可禁用或有可验证的上限及计费记录。超时但消耗未知时保守占用额度。无法证明每次请求受控，则工程门不通过；换会话/拆任务不能刷新任务族额度。

### 4.5 版本和部署成本需要实际验证

Python SDK 依赖同版本 runtime wheel，运行时可自带 Node；源码构建要求 Node ≥24.9.0，与运行 SDK 是两回事。根 npm 版本不能直接当成可安装 Python wheel 版本，必须核对目标平台的实际包及对应源码。[H1][H2]

采用时固定源码、SDK/runtime、profile、业务插件和模型配置版本，保存产物校验值；升级先通过协议/恢复回归。专用 TypeScript 插件加 Python 后端会增加跨进程调试和事件对账成本，能否抵消自建执行循环的成本尚未测定。

## 5. 候选架构与责任划分

```text
专用 React 工作台＋绑定业务对象的常驻对话
                 ↓ 查询 / ActionRequest
Python 业务服务：要求、证据、设计、版本、任务、预算、审核、放行
                 ↓ RuntimePort（拟建）
Harness Python SDK → 独立 runtime / 专用 profile / 业务插件
                 ↓ 注册模型适配器＋受限业务工具
          模型提供商 / 任务范围内的业务 API

PostgreSQL＋文件存储：权威业务状态、知识版本、产物、验收记录
Harness 会话存储：执行历史及恢复线索；关联到业务 Task/Attempt
```

运行时负责节内工具循环和模型交互；业务控制器负责跨步骤的 Do—Check—Loop。正文、写前设计、审核报告和摘要均先候选、再检查、再晋升。检查失败按原因返回设计、检索、补资料、修订或人工处理，不能由模型自行宣布任务通过。

每个写作/审核任务独立装配上下文；独立审核不接收作者的自评分。绑定记录至少包含 task/attempt、session、运行目录、配置/插件版本、输入指纹、ContextManifest 和预算归属。正常恢复复用同一逻辑任务及可恢复会话；会话损坏时从业务状态重建新 attempt 并记录关联，禁止重置额度或重复晋升结果。

采用后，Harness 取代原计划的模型工具循环和 LangGraph 执行层。数据库 worker、任务依赖、契约、版本、审核服务继续存在；同一任务不再同时由 LangGraph 和 Harness 编排，也不再叠加 ModelGateway 的第二套请求重试。向量调用仍由独立 embedding 客户端处理。

设置页继续管理写作/审核/摘要用途、提供商、模型、预算和数据范围，编译为版本化运行配置；摘要模型单独核对，不能假定根模型参数已覆盖。界面对话经 ActionRequest 路由，不能把原始聊天直接传给可执行 `/permission`、`/goal` 等原生命令的入口。[H2]

知识库与记忆管理继续由专用界面和业务库负责：已发布知识版本复用，项目决定独立确认，经验来自批准改稿且有适用范围。首次建设知识库需要真实企业材料；已有有效知识不要求每个项目重传。项目会话不是企业知识发布入口。

## 6. 对现有内容问题是否有直接帮助

| 用户反馈 | 必须落实的机制 | Harness 的作用及限制 |
|---|---|---|
| 没想清楚就写，方案飘 | 先形成可检查的方案机制、依据、能力/项目设计区分；不成立退回设计 | 能执行这段循环，不自带合格的方案判断标准 |
| 细目录拼点 | 每个细标题围绕完整业务问题；检查层级依据、相邻边界和响应映射 | 能保存/调用设计产物，目录质量仍需独立评审 |
| 覆盖齐但蜻蜓点水 | 分开记录提及、解释、证据；逐项核对必须回答的问题 | 能定向补读/补写，不能以循环次数或篇幅证明深度 |
| 作者说明、翻译腔 | 客户语言编辑；保留必要否定，编辑后复查语义变化 | 可编排编辑步骤；规则扫描仍有漏报和误报 |
| 凭空承诺或自设限制 | 核查正向保证与负向限制，新增责任/指标需来源或已确认决定 | 工具与提交门可阻断未核候选，不代表审核模型永不漏报 |
| 新项目反复重犯 | 保存批准改稿与缺陷反例；按适用范围检索；留出项目回归 | 可调用经验工具，收益来自业务记忆机制，不能归因于底座名称 |

这些机制也可以增强 Codex＋Skill。独立应用的预期优势是稳定地执行和记录业务约束；是否换来更少实质改稿，必须配对实测。

| H05 整本及留出验收 | 完整技术标＋未参与调试的项目；补遗三年改五年、跨章冲突、人工改稿、缺资料恢复、Word 渲染 | 当前版本响应矩阵、全文审核、全页检查、文件哈希及人工放行；留出评估 | T01—T30 有真实适用结果，无阻断/关键待核；整本及留出质量通过。缺真实材料为 blocked，不能用合成全绿替代 |

### 内容门如何定义

1. 先由业务评审冻结要求、关键证据、适用的必须回答问题和缺陷判据；专家批准改稿是评判参考，不能整段泄漏给对应留出任务。
2. 调试基准中的实质性遗漏、无据承诺/限制、旧客户事实、待核变已支持等预置阻断缺陷须全部检出；同时记录误报、漏报和检查分母，不将测试集零漏报推广为真实场景零漏报。
3. 三类真实章节的各次生成均须按原预算完成方案/细目录/内容验收；不能由人重写主体后记为自动写作通过。每次人工调整都记录范围、原因和耗时。
4. 专家逐项确认方案成立、业务问题已解释、关键表述有依据、面向客户、未增加无依据义务。任何一项关键待核都不能以综合高分抵消。
5. 对照现行 Codex＋Skill、增强业务流程的 Codex＋Skill、Harness 专用流程。尽量固定模型、材料、工具权限、业务判据和调用预算，随机化匿名稿件评审顺序。模型无法一致时分别报告模型与运行方式差异，不能声称已隔离 Harness 的贡献。
6. 采用收益门：硬缺陷和各内容维度不劣于增强对照，实质改写块占比与专家审改总耗时均降低，重复缺陷减少（对照已为零的类型保持零）；记录全部失败/重试和总费用。分段规则在评测前统一，实质改写指方案、事实、业务规则或响应内容变化，另记改写绝对量和原稿篇幅，避免靠加长正文降低比例。首批样本仅支持试点判断，留出项目用于复核稳定性。未满足时不能写成“质量和收益已证明”。

H04 的每类两次是早期内容门；H05/P16 最终评估仍遵守原计划的关键流程至少三次新 run、各方案至少一次整本及独立项目验收要求，不因本次候选验证降低基准。

质量损失函数沿用实施计划第 4.9 节：硬门槛先判，响应/事实/一致性/具体性/表达分别报告，再按固定规则比较候选；不通过模型自评分宣布质量。严重缺陷复检、全本一致性及文件验收继续独立执行。
